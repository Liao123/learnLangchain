# 模块 25：重建当前应用索引

## 这节课在学什么？

把你修改后的 Markdown 知识库，重新构建成 `rag_cli.py` 真正读取的父子索引 JSON。

一句话逻辑：

```text
修改 Markdown 原始资料
-> 重新切父章节和子片段
-> BGE 为新子片段生成向量
-> 覆盖应用索引 JSON
-> 索引 hash 变化，下一次启动自动使用新缓存版本
```

## 它解决什么问题？

前两课已经实现了“索引 JSON 内容变了，缓存版本自动变”。但只改 Markdown 文件还不够：`rag_cli.py` 不会直接搜索 Markdown，它读取的是：

```text
data/indexes/父子知识库索引.json
```

如果忘了重建索引，会出现这个问题：

```text
你改了 Markdown 的营业时间
-> 索引 JSON 还是旧内容
-> 程序仍按旧向量、旧父章节回答
-> hash 也不会变，因为被 hash 的索引 JSON 根本没变
```

## 当前应用实际使用哪份资料？

当前完整应用使用的是：

```text
原始资料：data/source/长文档示例.md
元数据：data/indexes/父子知识库元数据.json
应用索引：data/indexes/父子知识库索引.json
```

注意：`data/source/咖啡店知识库.md` 是前面短知识库课程留下的资料，不是当前父子 RAG 应用的输入文件。

当前原始资料里有 4 个完整父章节，构建后有 9 个子片段：

```text
parent_1 -> 退款办理规则          -> 3 个子片段
parent_2 -> 现制饮品与订单修改    -> 2 个子片段
parent_3 -> 会员积分与优惠        -> 2 个子片段
parent_4 -> 营业时间与到店服务    -> 2 个子片段
```

## 程序运行时发生了什么？

假设你把原始 Markdown 中“周六和周日的营业时间”改成新的时间：

```text
长文档示例.md
-> split("\n## ") 拆成 4 个完整父章节
-> 每章按约 100 个字符切成子片段
-> 得到 9 条 embedding_text
-> BGE encode() 得到形状大致为 (9, 512) 的向量
-> 写入 父子知识库索引.json
-> 整个 JSON 文件内容变化
-> SHA-256 hash 变化，例如 index-旧值 -> index-新值
-> 重启 rag_cli.py 后，旧缓存 key 不再命中
```

这里 hash 的对象仍然是**完整索引 JSON 文件**，不是单独的一段营业时间文字。因为完整父章节、子片段、父子关系和向量，任何一个变了都可能影响检索结果。

## 元数据为什么要检查？

`父子知识库元数据.json` 里保存着：

```json
{
  "parent_4": {
    "商品类型": "到店服务",
    "业务主题": "营业时间"
  }
}
```

如果你新增一个 `parent_5`，却没有添加它的元数据，后面的元数据过滤会出错。构建命令会先停止，并告诉你缺少哪个编号；这时旧索引不会被覆盖。

新增、删除或调整章节顺序时，也要人工检查这份元数据是否仍对应正确章节。因为 `parent_1`、`parent_2` 是按章节出现顺序生成的编号。

## 怎么运行和验证？

先运行本课 Demo。它会完整展开构建过程，但只在本课目录生成 `演示父子知识库索引.json`，不会改应用资料：

```powershell
py .\RAGDemo\lessons\25_重建当前应用索引\demo.py
```

确认输出包含：

```text
完整父章节数：4
可检索子片段数：9
BGE 向量形状：(9, 512)
```

然后，确实修改了 `data/source/长文档示例.md` 后，运行当前应用的构建命令：

```powershell
py .\RAGDemo\app\build_parent_child_index.py
```

最后重新启动完整应用：

```powershell
py .\RAGDemo\app\rag_cli.py
```

如果 Markdown 没有修改，重新构建后版本相同是正常的；这说明生成的索引内容没有变化。

## 这节要记住

- Markdown 是原始资料；索引 JSON 是 RAG 实际检索的资料包。
- 改 Markdown 后，必须重建索引，新的内容才会进入 RAG。
- 构建操作会调用 BGE，但不会调用 DeepSeek。
- 本课 `demo.py` 先把原始构建逻辑写开；实际应用命令在下一层 `app/` 中复用同一思路。
